# 权限模型

## 两种模式

由 `cjreg.toml` 的 `permission_mode` 控制：

| 模式 | 行为 |
|---|---|
| `open`（默认） | 持有有效发布 Token 即可发布（新包与新版本）；同版本不同 sha 仍返回 409，不静默覆盖 |
| `team` | 按**双路径**裁决（下节），新版本需 `write`，覆盖需 `overwrite` |

读鉴权由 `require_auth` 单独控制（默认关）：开启后 `GET /pkg`、`GET /index` 需要有效 Token
（会话或发布 Token 均可）+ 对资源的 `read` 权限。

## 双路径裁决（team 模式）

用户对某个包的**有效权限级别 = max(个人发布路径, 团队路径)**：

| 来源 | 级别 |
|---|---|
| 平台管理员（`isAdmin`） | overwrite(3) —— 直通 |
| **包名所有者（owner）** | write(2) |
| 团队成员（团队关联了该包或该组织） | 团队权限：read(1) / write(2) / overwrite(3)，多团队取最高 |
| 无关联 | 0（拒绝） |

### 包名所有者（owner）唯一

- owner = 该包**最早一条版本记录**的发布者（数据库 id 最小，含软删版本）；
- 协作发版只会把**新版本**的 `publisherId` 记为协作者（事实记录），**不会**产生新 owner，也不授予权限；
- 覆盖不转移所有权；硬删最早那条记录后 owner 顺延到下一条（等价于管理员间接转让）。

### 发布动态裁决

| 场景 | team 模式要求 |
|---|---|
| 新包，且命名空间**未被纳管**（无团队关联该组织或该包名） | 任意有效 Token 可认领，首次发布者成为 owner |
| 新包，命名空间已被纳管 | `write` |
| 已有包的新版本 | `write`（owner 天然具备） |
| 覆盖已存在版本（同版本、不同 sha） | `overwrite`（owner 不具备） |

> 组织 ID 语义：URL 里 `organization` 为空 = 「无组织包」（关联 ID 0）；填了但未在组织表中登记 = 不匹配任何组织关联
> ——避免「关联无组织」的团队越权到任意未登记组织。

## Token 与账号

| 机制 | 说明 |
|---|---|
| 会话 Token（`sess-*`） | 登录后签发（24h TTL），用于管理 API 与门户；可登出失效 |
| 发布 Token（`publish-*`） | 长期有效，写入客户端 `cangjie-repo.toml`；在门户 `/me` 查看/重置（重置后旧 Token 立即失效） |
| 口令存储 | pbkdf2（SHA512、90 万次迭代、16 字节随机 salt），对齐 cjcc 规范 |
| 多管理员 | 支持多个 `isAdmin`；禁止禁用或降级「最后一个启用管理员」（否则管理端将无人可登录） |
| 应急通道 | `cjreg admin reset-password`（重置口令 + 强制启用管理员） |

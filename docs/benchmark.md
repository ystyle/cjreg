# cjreg 性能基准

> 数据来源：`bash scripts/bench.sh`（标准档），原始输出在 `.smoke/bench/results/`。
> 定位：**单机 loopback 冒烟级基准**，反映服务端自身开销，**不是容量规划数字**。

## 0. 摘要

| 维度 | 结果 |
|---|---|
| 索引：回源 → 本地命中 | p50 **16.16 ms → 2.74 ms（5.9×）**；桩计数证明重查轮**零回源** |
| 制品下载（2 MiB，本地 blob） | p50 20.8 ms（回源 23.9 ms） |
| 发布吞吐 | 2 MiB **74 MiB/s** · 32 MiB **278 MiB/s** · 200 MiB **324 MiB/s** |
| 发布内存 | 三档 VmHWM **恒定 291 MiB**（与包体无关，流式发布成立） |
| 并发（索引命中态） | 1/4/16/64 VU → **88 / 294 / 414 / 356 req/s**（拐点在 16–64 VU 之间） |
| 生命周期 | 启动→可服务 **0.27 s** · SIGTERM 关闭 **0.03 s**（exit 0） |
| 下载（修复后） | 2 / 32 / **200 MiB** 全部下载成功且 **sha 一致（护栏 3/3）** |

## 1. 环境与方法

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen 7 7840HS（16 核） |
| 内存 | 29 GiB |
| 磁盘 | NVMe（`/dev/nvme1n1p2`） |
| 内核 | Linux x86_64 |
| 被测进程 | `target/release/bin/ystyle::cjreg`（`--static`），默认 GC 堆上限（未设 `cjHeapSize`） |
| 数据目录 | `.smoke/bench/data`（每次运行重建，**不使用生产数据**） |

**上游隔离**（本基准的关键前提）：真实中心仓有频率限制且网络会抖动，因此

1. 用 `scripts/bench-stub-upstream.py` 起一个**本地桩上游**（固定 5 ms 延迟、确定性制品、**请求计数**）；
2. 通过 `POST /api/admin/upstreams` 注册桩上游，并用 `PUT` 把 `official` 的**读路径开关** `proxyEnabled` 关掉。

`bench.sh` 在测量前**硬校验**：只要还有官方上游开着 `proxyEnabled` 就直接终止——否则请求会先打到真实中心仓（实测会引入 ~470 ms 的往返与重试，数据完全不可信），不会用被污染的数字出报告。

**口径说明**：单机 loopback，页缓存热；不含真实公网延迟、跨机房带宽、冷盘读。**所有"回源"都指向桩服务**。

复现：

```shell
eval "$(cjvs env zsh)" && eval "$(cjvs stdx-env zsh)"
cjpm build -j 16
bash scripts/bench.sh          # 标准档；quick 为快速档
```

## 2. 索引：回源 vs 本地命中（核心结论）

100 个本地都不存在的包（每个首次必然回源），再对同一批包重查一遍：

| 档位 | p50 | p95 | p99 | avg |
|---|---|---|---|---|
| 回源（本地无） | **16.16 ms** | 21.64 ms | 24.87 ms | 16.04 ms |
| 重查（应命中本地） | **2.74 ms** | 4.80 ms | 8.80 ms | 3.01 ms |
| 本地发布的包 | 3.12 ms | 4.74 ms | 7.74 ms | 3.32 ms |

**桩服务请求计数**：`0 → 100 → 100` —— 回源轮 100 次（一包一次），**重查轮增量 0**、本地发布轮增量 0。

延迟变小可能只是"这次没卡"，计数才是硬证据：**重查轮确实一次都没回源**。索引落库后，同一包的后续查询走 `IndexService.generate` 本地生成，比回源快约 **5.9×**（差距主要来自上游往返，桩已固定 5 ms）。

## 3. 制品下载

| 档位 | p50 | avg |
|---|---|---|
| 回源（首次） | 14.8–23.9 ms | 16.7–26.2 ms |
| 本地 blob 命中 | 14.4–20.8 ms | 14.4–24.0 ms |

2 MiB 制品下两者接近：回源延迟（桩 5 ms + 传输）与本地 blob 读取 + 响应写入处在同一量级。制品是内容寻址的，**换组织查同一制品也命中同一 blob**。

单包实测（本地发布、无回源参与）：2 MiB → **18 ms**、32 MiB → **28 ms**（≈1.2 GB/s，页缓存热）。

## 4. 发布吞吐与内存

| 制品 | HTTP | 耗时 | 吞吐 | 进程 VmHWM |
|---|---|---|---|---|
| 2 MiB | 200 | 0.027 s | 74 MiB/s | 291 MiB |
| 32 MiB | 200 | 0.115 s | 278 MiB/s | 291 MiB |
| 200 MiB | 200 | 0.618 s | **324 MiB/s** | **291 MiB** |

三档 VmHWM **完全一致**：发布链路是流式的（边读边算 sha256 并落临时文件），内存占用与包体无关。固定开销 ≈ GC 堆上限（256 MB）+ 原生内存（badger arena 等）。

## 5. 并发扩展性（索引命中态）

| 并发 | 请求数 / 10 s | ≈ req/s | p95 |
|---|---|---|---|
| 1 VU | 881 | 88 | 12.6 ms |
| 4 VU | 2948 | 294 | 14.5 ms |
| 16 VU | 4140 | 414 | 24.0 ms |
| 64 VU | 3566 | **356**（回落） | **114 ms** |

吞吐在 16 VU 附近见顶，64 VU 时吞吐下降、p95 从 24 ms 恶化到 114 ms：服务端是单线程事件循环，超出处理能力后请求排队，延迟线性上升而吞吐不再增长。**扩展靠多实例 + 前置负载均衡，而不是继续加压单实例。**

## 6. 生命周期

| 指标 | 值 |
|---|---|
| 启动 → 可服务 | **0.268 s** |
| SIGTERM → 退出 | **0.031 s**，exit code **0** |

关闭走 `runShutdownHooks()` → `close()`（flush 落盘）→ `exit(0)`；秒级完成说明关闭路径没有被卡住。

## 7. ⚠️ 发现与待办

**① 下载路径整包驻留内存 → 200 MiB 下载 `Out of memory` —— ✅ 已修复**

发布已经流式化，**下载没有**:请求处理里把制品整体读成 `Array<Byte>` 再写出响应，峰值约为制品 2–3 倍。实测（本地发布的包、无回源参与）：

| 制品 | 结果 |
|---|---|
| 2 MiB | 200 · 18 ms |
| 32 MiB | 200 · 28 ms |
| 200 MiB | **超时 45 s、0 字节；服务日志 `Out of memory`** |

官方协议允许单段 500 MB，因此**下载侧曾是兑现协议上限的短板**（发布侧已达标）。

**修法**（与发布同构）：`BlobStore` 新增 `stream(sha256): ?InputStream`（磁盘实现直接给出 `File` 流，
内存实现用 `BytesStream` 包装）；`ProxyService` 新增 `fetchArtifactStream`（本地命中直接给 blob 流，
回源仍先落 blob 但**不再把字节交给调用方**）；下载 handler 改为 `ctx.responseBuilder.body(stream)`。

**修复后实测**（同一 `bench.sh`）：发布 2 / 32 / 200 MiB → 0.029 / 0.116 / 0.626 s、VmHWM 恒定 284 MiB；
**随即下载这三个包全部成功且 sha 一致（护栏 3/3）**，此前同一条护栏只有 1/3（32 MiB 与 200 MiB 均超时）。

代价：流式路径不再顺手做制品内 README 提取（那需要把制品读进内存，与流式互斥）。
已补齐的文档不受影响；需要补时走 `admin sync-metadata` 或再次触发回源聚合。

**② 大包发布后堆占用未回落 —— 随 ① 一并消除**

修复前：同一次运行里 200 MiB 发布成功后，连 32 MiB 下载也超时（单独重启后只要 28 ms）。
下载改为流式后，同一序列（200 MiB 发布 → 200 MiB 下载 → 32 MiB 下载）全部通过，
说明此前是**下载路径把堆顶满**，而非发布侧泄漏。若后续在大对象场景再观察到堆不回落，
再按 `claimFile` 临时缓冲 / GC 阈值方向排查。

**③ 并发拐点**

见 §5：16 VU 之后吞吐不再增长。当前实现单线程事件循环，这是预期行为；若要提高单实例上限，需要把耗时操作（哈希、磁盘 IO）挪出事件循环。

> ①②是**功能性风险**（协议上限无法兑现、且会影响后续请求），已记入 `AGENTS.md` 待办；本报告先给出可复现证据与定位方向。

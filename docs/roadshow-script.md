## 3. 六步现场演示（只演示「看得见价值」的）

每步都遵循：**先说要看什么 → 操作 → 指着结果说结论**，不解释实现细节（留给答辩）。

1. **部署**：`docker compose up -d` → 健康检查返回 ok → `/api/stats` 里 `serverVersion=0.3.0`
   （一句话：单二进制 + 数据卷，重启数据留存，`docker stop` 走优雅关闭）
2. **发布 200 MiB 大包**：`time cjpm publish`（约 0.6 s）→ 立刻 `ps -o rss= -p <pid>`/仪表盘看内存
   （一句话：内存恒定 291 MiB，与包体无关 —— 这是初赛版本做不到的）
3. **索引与多仓**：`cjpm update` 第一次回源生成索引，第二次同一包走本地（快 5.9×）；
   「解析诊断」页面直接告诉你：哪个仓有、你该发到哪
4. **发布计划**：创建 → 自动补齐依赖（拓扑序）→ 版本对照 → 执行；页面实时进度（SSE）→ 空站收到包
5. **权限**：`alice` 发新版本 OK；`bob` 越权 → 403；审计页两条记录（成功/失败）并排看
6. **三级删除 + 公开 API**：软删后下载 404 → 恢复 → 硬删（制品清理）；
   `curl /api/packages` 一条命令给 CI 用

> 每步都留一句「兜底话术」：万一某步卡住，立刻改口讲「这一步的结果在这张截图/这段录屏里」，
> 然后跳到下一步，不要在台上 debug。

## 6. 答辩 Q&A（按出现概率排序）

**Q1 和官方中心仓是什么关系？为什么需要私有仓？**
协议互通（发布/下载/索引同一套），不是替代而是补位：①内网/离线环境；②发布不可逆 + 同步不可控 →
需要预演仓；③多仓体系（官方 + 私有 + 团队仓）与依赖推送到多个目标。生产实例内网常驻，团队日常在用。

**Q2 大包流式具体怎么做的？**
请求体不再整包读入：按段解析头 → 边读边算 sha256 → 直接写临时文件 → 校验后 `rename` 原子落盘；
下载侧 `BlobStore.stream` + handler 直接 `body(stream)`；回源同样流式落盘。峰值内存与包体无关（200 MiB 实测 291 MiB）。

**Q3 为什么选 bstorm / badger（LSM）而不是 SQLite？**
**直接原因是当时的生态约束：写这个项目时仓颉还没有完整可用的 SQLite 驱动**（原生绑定不成熟），
所以选了当时唯一成熟的纯仓颉 LSM 方案 bstorm/badger —— 无 C 依赖、静态单二进制。
事后看也合适：包/版本/审计都是 KV + 内容寻址 blob，事务与恢复语义够用；
写入 `syncWrites` + 优雅关闭 flush 保证不丢已确认写入。

**Q4 权限模型为什么是「首个发布者即 owner」？**
包名归属唯一、可追溯；团队 write/overwrite 与管理员直通并存；退出团队后不可见是**有意的产品决策**（私有仓）。
覆盖不转移所有权；越权 403 与失败审计都落在日志里。

**Q5 1002 个用例怎么组织的？为什么覆盖率能到 91.3%？**
三层：纯逻辑单测（协议/索引/权限/存储）→ **进程内 HTTP 夹具**（起真实服务 + 真实 client，覆盖 handler）→
页面渲染测试（cjxt 组件树断言）。UI/handler 不再靠 e2e 兜底，所以分母涨了覆盖率也涨了。

**Q6 性能数据可信吗？**
`scripts/bench.sh` 一键复现：桩上游固定 5 ms 延迟 + k6 并发；内存取 `/proc/<pid>/status` 的 `VmHWM`；
计数证明「重查轮零回源」。环境与口径写在 `docs/benchmark.md` 开头。

**Q7 生产上跑得怎么样？**
内网实例常驻（8066），管理端 + 门户日常在用；含真实包与审计；镜像 `ghcr.io/ystyle/cjreg:v0.3.0` 可直接起。

**Q8 都没做什么？**
arm64 镜像、镜像瘦身（现 507 MB）、镜像预热/周期同步、K8s 清单。这些都在计划里，属工程完善而非功能缺失。

**Q9 仓颉版本适配？**
`v0.3.0` 用 Cangjie **1.2.0** 构建（`cjc-version` 声明 1.1.3）；`v0.2.0` 及以前的产物由 **1.1.3** 构建。
本项目是可执行程序、不向中心仓发布库制品，所以 ABI 兼容不是约束；两版工具链的构建验证见
[`finals-submission.md`](finals-submission.md)（若 1.1.3 验证通过会补上数字）。

**Q10 AI 工具怎么用的？**
开发期用 Agent 辅助重构（handler 拆分、DTO 化）、批量补测试（handler 夹具 + 页面渲染）、
写文档与复盘；AI 只做执行，取舍与验收由人定（例如「测试不许弱化」的约束）。

**Q11 为什么自研 tar/gzip 解压？**
要在发布/回源路径上从制品里提取 README 与 `cjpm.toml`（索引协议不带这些字段）；
`stdx.compress.zlib` + 自研 `ystyle::tar` 避免引入 C 依赖，保持单二进制。

**Q12 发布计划为什么需要「等索引」？**
目标仓落库后索引可能延迟；因此判据是**版本出现且 sha256 一致**，否则计划会假完成。六态 + SSE 让等待可见、可跳过。

**Q13「多仓体系」到底是什么？会不会被理解成一个实例托管多个仓？**
不是托管，是**对接**：一个 cjreg 实例同时对接多个外部仓，但分两条互不相干的路——
读路径（`enabled && proxyEnabled`，用于回源/镜像/解析诊断/重拉）与写路径（`enabled && asTarget`，
发布计划的目标下拉）。`enabled` 是总闸；官方仓默认参与回源、但**默认不是**推送目标（推官方不可逆，要显式授权）。
界面上一个上游有三个开关，正是这三件事。

**Q14「解析诊断」和「该发到哪」是一回事吗？不是。**
- 解析诊断（`GET /api/admin/resolve`）回答「这个依赖能不能解析、从哪个上游解析到、版本/sha 是多少」：
  按 priority 遍历回源链，取索引、找满足 `require` 的最高版本、命中即停，每一步进 `trace`，并标出跨仓
  同版本不同 sha 的 `conflict`；
- 「该发到哪」由**发布计划**的版本对照回答：选好目标仓后去取它的索引，把每个包分成
  `need_publish / already_exists / conflict / version_optional`——该发不该发一目了然，但**目标是人在创建计划时选的**，
  系统只负责摊开依据。目标仓取不到索引时单独标 `target_error`，不会假装"目标仓没有"。

**Q15 多仓会不会把官方仓全量镜像到本地？**
不会全量同步：只有被请求（下载或索引查询）的包才懒加载落本地，并带 `cacheTtl`；重拉（refetch）
只对回源版本生效，且上游 sha 变了要 `force=1` 才覆盖。

# 发布计划

**发布计划 = 依赖分析（拓扑排序）+ 按序推送 + 结果校验**，用于「一次升级底层库后批量发布整条依赖链」或
「把本地包批量转发到官方/另一个私有仓」。

## 流程

1. **创建计划**：选择目标上游（`target_url` 或计划绑定的上游）；
2. **analyze**：`POST /api/admin/publish-plans/analyze`，输入根包（`org::name@version`），
   复用 cjdep 的依赖分析能力输出拓扑顺序与四分类：

   | 分类 | 判定 |
   |---|---|
   | `need_publish` | 目标仓无此版本 |
   | `version_optional` | 存在更高版本或部分版本缺失 |
   | `already_exists` | 版本相同且 SHA-256 相同 |
   | `conflict` | 版本相同但 SHA-256 不同 |

3. **勾选 items → 执行**：`POST /api/admin/publish-plans/execute`，按 order（依赖先于依赖者）串行推送；
4. **校验**：推送后按目标仓索引确认「版本出现 **且 SHA-256 一致**」，不一致不算成功；
5. **容错**：支持暂停/继续、失败重试、手动跳过；**服务重启时把 `running`/`paused` 计划复位为待执行**，避免悬挂。

## 认证与目标仓

- 推送到需要认证的目标仓时，请求体可带 `target_token`；
- 未显式提供时，服务端会按 `target_url` 匹配上游表，取该上游的 `authToken`（因此把目标仓登记为上游即可自动带上 token）。

## 界面

管理后台 → **发布计划**：创建向导、详情页查看每个 item 的执行状态与错误、开始/暂停，
进度通过服务端推送实时更新。

## e2e 验证

`tests/e2e.sh` 用 6 个真实依赖包验证完整链路：

```
A(18060) 发布 6 包 → analyze 展开拓扑 → execute 推送到 B(18070) → 校验 B 的索引/制品/依赖
```
